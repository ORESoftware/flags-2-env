# ADR 0001: target-qualified prebuilt C artifacts

Status: proposed  
Date: 2026-08-07  
Tracking: Linear DEN-2845; GitHub issue #29

## Context

`flags-2-env` currently tracks generated Mach-O objects and libraries in `build/`. A Linux consumer can invoke a partial build and accidentally link those stale host artifacts, producing a misleading source/linker failure. The package also needs an offline path for consumers that install it as a Git submodule or through zed-pkg.

Generated intermediates and reviewed release artifacts therefore need different locations, provenance, and validation rules.

## Decision

### Canonical target identities

Rust/LLVM-style target triples are authoritative in the Make interface, directory layout, generated manifest, zed selector, lockfile, CI matrix, and release evidence.

Tier 1:

- `aarch64-apple-darwin`, minimum macOS 11.0;
- `x86_64-apple-darwin`, minimum macOS 10.15;
- `x86_64-unknown-linux-gnu`, minimum glibc 2.28;
- `aarch64-unknown-linux-gnu`, minimum glibc 2.28;
- `x86_64-unknown-linux-musl`, minimum musl 1.2.2; and
- `aarch64-unknown-linux-musl`, minimum musl 1.2.2.

`armv7-unknown-linux-gnueabihf` is Tier 2/experimental until a named consumer owns a native or emulated runtime lane. Windows, WASI, and 32-bit x86 remain deferred for the same reason.

`prebuilt/targets.json` is the machine-readable target/tier authority. A target cannot move to Tier 1 unless it has a nonempty fixture owner and its runtime lane is a release gate.

### Layout

Reviewed artifacts live under:

```text
prebuilt/
  targets.json
  manifest.schema.json
  manifest.json                 # generated by the build/release slice
  <canonical-triple>/
    libflags2env.a
    libflags2env.{so|dylib}
```

`build/` remains generated scratch space and will be removed from Git plus ignored atomically when the first complete Tier 1 artifact set is committed. This ADR does not move the existing bytes by renaming them because their target, toolchain, ABI, and source provenance have not yet been certified.

### Artifact kinds and ABI

Tier 1 initially publishes both static and shared libraries. Evidence from downstream fixtures may justify pruning a kind in a later ADR.

The generated manifest carries an integer `abi_version` and a digest of the normalized exported-symbol set. Any removed or incompatibly changed exported symbol requires an ABI-version bump and consumer migration evidence. A stable filename must never conceal an ABI break.

Shared libraries record ELF SONAME or Mach-O install name. Every artifact records its minimum runtime/platform floor.

### Provenance and reproducibility

Each manifest artifact records target, kind, path, size, SHA-256, exported-symbol digest, compiler, linker, archiver, SDK/sysroot, normalized flags, and platform floor. The top-level manifest records source commit, source-input digest, `SOURCE_DATE_EPOCH`, package version, and ABI version.

The source-input digest covers C sources, public headers, build scripts, target configuration, export maps, and manifest-generation logic.

Linux GNU/musl builds use a pinned Zig toolchain. Darwin builds use a pinned native Xcode/clang environment until a Darwin cross-toolchain can prove SDK provenance, legal redistribution, linker behavior, signing, and native loadability.

Reproducibility means two independent clean builds produce identical normalized unsigned bytes. Darwin signing is validated after that comparison; refreshing a manifest hash is not evidence of reproducibility.

### Repository budgets

Starting limits:

- 1 MiB maximum per committed artifact;
- 10 MiB maximum for the current `prebuilt/` tree; and
- 5 MiB maximum Git-history growth per release.

Exceeding a limit requires an approved exception or moves new bytes to immutable GitHub Release/R2 assets referenced by digest. Externally hosted bytes require signature/provenance verification and content-addressed local caching. Git LFS is not used.

### Installation behavior

The package exposes three explicit modes:

- `auto`: use a verified matching prebuilt, otherwise explain and build from source;
- `prebuilt`: require a verified matching artifact and fail closed; and
- `source`: ignore prebuilts and compile from source.

Host detection is only a default. Cross-build/container consumers can request an explicit target triple. The lockfile records the requested target, artifact kind, ABI version, and digest.

zed-pkg selection is a typed target/artifact selector. User-facing target templates may compile into that model, but arbitrary path interpolation is not part of the trust boundary.

## Consequences

- Offline/submodule consumers keep a self-contained install path.
- Wrong-host objects cannot masquerade as fresh generated output.
- Repository growth is accepted only within explicit budgets.
- The first artifact release requires native/emulated runtime lanes, ABI checks, independent reproducibility builds, and migration of all twelve consumer fixtures.
- This ADR alone does not certify or relocate the currently tracked `build/` artifacts.
